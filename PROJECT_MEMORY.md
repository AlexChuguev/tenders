# Project Memory

Это не обзор проекта, а набор жёстких правил интерпретации. Если код и этот документ расходятся, это баг пайплайна.

## 1. Цель таблицы

`tender_analysis.xlsx` — рабочий файл пользователя.

Для новых выгрузок система должна:
- добавлять новые строки, а не удалять старые;
- не перетирать пользовательские статусы и комментарии;
- сортировать внутри вкладки по дате окончания подачи;
- сохранять ссылку на карточку закупки, ссылку на папку выгрузки и ссылки на документы, если они есть.

## 2. Что считается системным багом

Системный баг, а не частный случай:
- стек явно есть в документе, но в summary написано `стек не извлечён`;
- требования к контрагенту явно есть в документе, но в summary написано `не указано`;
- модификация существующей системы не отражена в summary;
- интеграция/подключение к существующей ИС ошибочно трактуется как новая разработка;
- непрофильный industrial/SCADA/PLC кейс не уходит в непрофильный класс;
- аутстафф/предоставление специалистов не распознаётся как отдельный тип закупки;
- summary формулирует выводы, которые не подтверждаются документами;
- rebuild/re-render меняет пользовательский статус;
- XLS row -> folder -> artifact -> Excel row не сшиваются однозначно.

Точечные правки по одному тендеру запрещены как стратегия. Ошибка должна лечиться в taxonomy, extraction, quality gates или stitching.

## 3. Базовые классы закупок

### 3.1 Профильные

Сюда относятся:
- разработка ПО;
- доработка информационных систем;
- развитие web/mobile продуктов;
- backend/frontend/mobile разработка;
- проектная разработка с AI/LLM, если предмет — именно создание/доработка продукта.

### 3.2 Непрофильные

Сюда относятся:
- промышленная автоматизация;
- АСУТП / SCADA / PLC;
- электроучёт / АСКУЭ;
- строительно-монтажные и пусконаладочные работы;
- чистое обучение, консалтинг, исследование рынка;
- поставка коробочного решения без нормального контура разработки.

Если документ явно указывает на `TIA Portal`, `CoDeSys`, `WinCC`, `Movicon`, `IEC 61131-3`, `LAD`, `SCL`, `LD`, `ST`, `SCADA`, `PLC`, `АСКУЭ`, `электроучет`, это не наш профиль.

## 4. Legacy / integration / outstaff

### 4.1 Legacy modification

Если предмет — развитие, модификация, доработка, оптимизация, расширение существующей системы, это должно явно отражаться в summary.

Фразы-маркеры:
- `доработка`
- `модификация`
- `развитие`
- `расширение функциональности`
- `в части доработки`
- `существующей системы`
- `текущей системы`

### 4.2 Integration-only

Если документ говорит про подключение, обмен, интеграцию, сопряжение, API-взаимодействие с существующей ИС, это не равно новой разработке.

Это должно отражаться как:
- `подключение к существующей ИС (интеграция)`

### 4.3 Outstaff-like

Не нужно упираться в слово `аутстаффинг`. Важен смысл.

Если закупка про:
- предоставление специалистов;
- выделение команды;
- почасовую загрузку разработчиков;
- роли и ставки;
- внешние ИТ-ресурсы;
- подрядчиков на усиление команды;

это отдельный класс. Если стек не указан явно, в рисках нужно писать, каких ролей не хватает относительно нашего core:
- mobile / Flutter
- frontend / React
- backend / Python
- и какие ещё роли явно требуются документом.

## 5. Что писать в summary

Сейчас активные рабочие пункты:
- `1. Стек`
- `2. Требования к контрагенту`

Текст должен быть короткий и фактологичный.

Запрещено:
- писать абстракции вроде `требования к команде; сертификаты;`;
- писать `не указано`, если требования есть в документе;
- писать `стек не извлечён`, если стек читается из первых страниц или из ТЗ;
- добавлять неподтверждённые технологии.

### 5.1 Стек

В стек попадают:
- языки;
- фреймворки;
- платформы;
- runtime / CMS / ERP / industrial среды, если они прямо определяют профиль закупки.

Если явного стека нет, но тип работ однозначно указывает на непрофильную инженерную область, это нужно отражать не как пустой стек, а как распознанный тип среды.

Пример:
- если это PLC/SCADA-доработка, summary не должен говорить `стек не извлечён`.

### 5.2 Требования к контрагенту

Нужно писать только то, что реально подтверждается документом:
- СРО;
- оборот;
- опыт аналогичных проектов;
- опыт доработки существующих систем;
- наличие специалистов/ролей;
- лицензии/сертификаты;
- иные квалификационные документы.

Если ничего явного нет, писать `не указано`.

Не писать:
- `требования по опыту и финансам требуют проверки`, если документ просто молчит;
- `кадровые ресурсы`, если по смыслу имеется документ о кадровых ресурсах.

## 6. Документы и доказательства

Summary должен строиться из фактов, а не из красивого текста.

Для каждого вывода желательно иметь evidence:
- файл;
- фрагмент;
- страница, если доступно.

Если доказательств нет, вывод должен быть слабее или должен сработать quality gate.

## 7. Excel и владение полями

Пользовательские поля:
- `Статус`
- `Комментарий`

Система не должна их перетирать при rebuild/rerender.

Системные поля:
- `Summary`
- `Наименование лота`
- `Дата окончания приема заявок`
- `Выгрузка`
- `Факты:*`

## 8. Обязательные проверки после изменений правил

Любое изменение extraction/taxonomy/summary/Excel stitching должно проверяться через:
- `run_regression_pack.py`
- batch completeness audit
- diff артефакта против deterministic rerender

Если regression не зелёный, изменение считается недействительным.

Новый реальный баг не должен оставаться только в переписке. Его нужно превращать в regression case.

Минимальный цикл:
- найти artifact проблемного тендера;
- сгенерировать skeleton через `create_regression_case.py`;
- добавить кейс в `regression_pack.json`;
- убедиться, что баг воспроизводится тестом;
- чинить код;
- вернуть regression pack в зелёное состояние.

## 9. Приоритеты улучшений

Следующие системные усиления по приоритету:
- нормализация требований к контрагенту в структурные поля;
- разделение `extract -> classify`;
- quality report по батчу;
- расширение golden set;
- структурное evidence-хранилище.
